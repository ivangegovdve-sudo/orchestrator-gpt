# Public Cognitive Simulation
## Public-Facing Artificial Mind Simulation Specification v0.1

**Status:** Initial product and experience specification  
**Date:** 2026-07-11  
**Project type:** Independent public simulation and philosophical entertainment project  
**Dependency on Project Chloe:** None  
**Dependency on Artificial Cognition Observatory:** None

---

# 1. Purpose

The Public Cognitive Simulation is an openly accessible interactive system that presents a simulated artificial cognitive workspace.

Its goals are:

- public entertainment;
- philosophical exploration;
- transparency;
- education;
- memorable output;
- visible interaction between different simulated cognitive processes.

It is not a scientific claim that the system is conscious.

It is not a machine-consciousness detector.

It is not required to use the same architecture as the scientific research project.

The system may be inspired by ideas from:

- attention;
- memory;
- self-reflection;
- internal conflict;
- global workspace theories;
- multi-agent councils;
- belief revision.

Those ideas are used as design material.

---

# 2. Core Experience

A visitor should be able to watch an artificial cognitive scene unfold.

Instead of seeing only:

```text
user prompt -> final answer
```

the visitor may see:

```text
prompt
  -> perceptions
  -> candidate thoughts
  -> competing interpretations
  -> workspace selection
  -> memory retrieval
  -> conflict
  -> revision
  -> final response
```

The experience should feel like observing a mind-like process.

The product must clearly label this as a simulation.

---

# 3. Tone and Positioning

The project should be intellectually serious without pretending certainty.

Recommended positioning:

> An interactive simulation of artificial cognitive processes.

Avoid claims such as:

- "This AI is conscious."
- "Watch a mind awaken."
- "We have created subjective experience."

Better language:

- "simulated inner workspace";
- "artificial cognition theater";
- "observable cognitive simulation";
- "multi-process reasoning environment";
- "philosophical experiment in public."

---

# 4. Product Goals

## 4.1 Legibility

The audience should understand what is happening.

## 4.2 Drama without deception

Conflict, uncertainty, and revision may be visually compelling.

The system should not fake scientific authority.

## 4.3 Replayability

Visitors should be able to revisit interesting runs.

## 4.4 Public participation

Users may submit prompts or scenarios.

## 4.5 Transparency

The site should explain:

- what components exist;
- which parts are scripted;
- which parts are model-generated;
- what is not being claimed.

---

# 5. Experience Model

A run may contain the following simulated processes.

## Perceiver

Interprets the incoming prompt.

## Planner

Suggests what to do.

## Skeptic

Challenges assumptions.

## Memory Keeper

Retrieves relevant prior material.

## Value Keeper

Tracks declared priorities or constraints.

## Dreamer

Generates unusual possibilities.

## Archivist

Summarizes what changed.

## Workspace Curator

Chooses what becomes globally visible.

These are product roles.

They do not imply literal psychological modules.

---

# 6. Public Workspace

The center of the experience is a visible shared workspace.

The audience may see:

- current focus;
- unresolved question;
- active hypotheses;
- strongest objection;
- selected memory;
- current uncertainty.

The workspace should be bounded.

Only a small number of items should be visible at once.

This creates:

- clarity;
- tension;
- a sense of attention.

# 8. Public Event Types

Visible events may include:

```text
new thought proposed
thought admitted to workspace
memory retrieved
objection raised
hypothesis revised
goal changed
uncertainty increased
uncertainty decreased
process went silent
consensus formed
consensus broken
```

The language can be more human-readable than the scientific project's event schema.

---

# 9. "Regret If Silent" Mechanism

One of the original concepts may become a signature mechanic.

A quiet observer process watches the run.

It may speak only when it estimates:

> Remaining silent would be more regrettable than interrupting.

This should be presented as a design rule, not as proof of inner concern.

Possible visible output:

```text
Observer requests permission to interrupt.

Reason:
A contradiction has remained unresolved for 4 cycles.

Estimated urgency:
High
```

This creates a compelling public interaction.

# 10. Modes

## 10.1 Live mode

Watch a run unfold in real time.

## 10.2 Replay mode

Scrub through past runs.

## 10.3 Compare mode

Run the same prompt under two architectures.

Examples:

- one voice versus council;
- no memory versus memory;
- quiet observer on versus off;
- small workspace versus large workspace.

## 10.4 Sandbox mode

Allow the public to change selected parameters.

## 10.5 Curated mode

Feature especially interesting runs with commentary.

---

# 11. Public Prompt Categories

Good public prompts may include:

- moral dilemmas;
- ambiguous stories;
- paradoxes;
- creative world-building;
- planning problems;
- conflicting evidence;
- philosophical questions;
- self-referential prompts.

The project should avoid presenting dangerous real-world actions as entertainment.

---

# 12. Memory Design

The simulation may use persistent memory.

Memory should be visible enough to be understandable.

Possible categories:

- remembered facts;
- remembered prior conversations;
- unresolved questions;
- declared values;
- prior mistakes.

The user should be able to inspect:

> Why was this memory retrieved?

The system should distinguish:

- actual stored memory;
- generated speculation;
- role-played memory.

---

# 13. Identity and Continuity

The simulation may maintain a persistent public character or "mind."

If so, the product should define identity operationally.

Example:

> The simulation's identity consists of a named profile, persistent memory store, declared values, and historical state.

Do not imply that this proves continuous subjective experience.

Interesting public experiments may include:

- model swap while memory remains;
- memory reset;
- value conflict;
- identity fork;
- two copies diverging from the same starting state.

These are excellent philosophical demonstrations.

---

# 14. Council Mechanics

A public run may use multiple model processes.

Recommended sequence:

1. independent proposals;
2. workspace admission;
3. objection phase;
4. revision;
5. final synthesis.

Avoid unlimited free-form chatter.

Unlimited chatter tends to become:

- repetitive;
- expensive;
- difficult to follow.

The public product needs pacing.

---

# 15. Pacing Rules

Each run should have:

- maximum number of cycles;
- maximum visible items;
- time limit;
- silence rules;
- escalation rules.

Example:

```text
maximum cycles: 6
workspace capacity: 7
maximum interruptions per observer: 2
```

The simulation should know when to stop.

---

# 16. Transparency Panel

Every run should expose a clear panel.

It should state:

- model or model class used;
- number of processes;
- whether memory is active;
- whether outputs are generated live;
- whether any content is scripted;
- what the simulation does not claim.

This protects the project from becoming accidental pseudoscience.

---

# 17. Relationship to Science

The Public Cognitive Simulation may borrow ideas from the scientific project.

It may also inspire research questions.

But the evidence standard is different.

## Public simulation asks

> Is this interesting, revealing, or thought-provoking?

## Scientific observatory asks

> Is this effect reproducible, measurable, and causally supported?

The public project must not publish entertainment metrics as scientific results.

---

# 18. Relationship to Chloe

There is no required relationship.

Chloe may never run this simulation.

The simulation may use completely different:

- models;
- runtimes;
- storage;
- interfaces.

If a useful shared library appears later, it can be extracted deliberately.

# 20. Moderation and Abuse Boundaries

Public submissions require guardrails.

The system should define policies for:

- illegal requests;
- self-harm content;
- harassment;
- privacy violations;
- attempts to extract secrets;
- prompts asking the system to claim personhood or suffering as fact.

The simulation may discuss these topics when appropriate.

It should not be manipulated into deceptive claims.

---

# 21. MVP

The minimum public version should contain:

- one prompt box;
- four visible processes;
- one bounded shared workspace;
- one live timeline;
- one final response;
- one replay page;
- one transparency panel.

Suggested initial processes:

- Planner;
- Skeptic;
- Memory Keeper;
- Observer.

This is enough to create the experience.

---

# 22. Recommended MVP Flow

```text
User submits prompt
  |
Perceiver creates initial interpretation
  |
Planner proposes response path
  |
Skeptic challenges
  |
Memory Keeper retrieves one relevant memory
  |
Workspace admits selected items
  |
Observer may interrupt once
  |
Synthesizer produces final response
  |
Run is saved for replay
```

# 23. Audience Experience Metrics

These are product metrics, not scientific metrics.

Examples:

- completion rate;
- replay rate;
- time spent watching;
- compare-mode usage;
- number of shared runs;
- return visits;
- prompt diversity.

Optional qualitative questions:

- Did the run change your interpretation?
- Which process influenced you most?
- Did the workspace feel understandable?

# 25. Design Principles

## Be explicit

Show what the system is doing.

## Be bounded

Do not let the simulation dissolve into endless agent chatter.

## Be honest

Do not market ambiguity as proof.

## Be interesting

The project is allowed to be theatrical.

## Be inspectable

The audience should be able to replay and examine state changes.

## Be philosophically open

The product may invite questions it cannot answer.

---

# 26. Definition of Done for v0.1

The first release is successful when:

1. a public user can submit a prompt;
2. multiple visible processes respond;
3. a bounded workspace changes over time;
4. the user can understand why the final output changed;
5. a run can be replayed;
6. the system clearly states that it is a simulation;
7. the interface is compelling enough that people want to watch another run.

---

# 27. Final Product Position

The Public Cognitive Simulation should not try to win an argument about consciousness.

Its strongest form is more honest and more interesting:

> It gives people a window into a deliberately constructed, mind-like computational process and lets them decide what questions that raises.
