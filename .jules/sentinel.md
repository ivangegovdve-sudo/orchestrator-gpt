## 2024-03-28 - Fix XSS Vulnerability in Accordion Component
**Vulnerability:** The vanilla JavaScript accordion component in `web/ai-init/app.js` was rendering a dynamically provided variable directly into the DOM using `right.innerHTML = String(count) + " <span class=\"accordion-chevron\">></span>"`. While `count` was intended to be numeric, injecting variables without escaping or structured element creation via `innerHTML` opens a potential pathway for XSS attacks if the value is ever influenced by un-sanitized upstream data.
**Learning:** Using string concatenation combined with `innerHTML` in vanilla JS is inherently risky, even for seemingly numeric values, as upstream schema changes or API behavior could later introduce unsanitized strings.
**Prevention:** Consistently favor safe DOM APIs like `document.createElement`, `textContent`, and `.appendChild()` when rendering dynamic data to guarantee text evaluation rather than HTML evaluation.

## 2026-08-26 - [CRITICAL] Fix javascript: URI XSS in Library Search results
**Vulnerability:** The library search components (`web/library/shared.js`, `web/library/rag.html`, and `web/library/repos/index.html`) were generating `<a>` tags where the `href` attribute was constructed directly from an external URL field (like `result.meta.url`). While the link text (the title) was correctly escaped, the `href` attribute itself was not validated against safe protocols, opening a potential pathway for XSS attacks if a malicious source injected a `javascript:...` URI.
**Learning:** Escaping HTML entities on text content is insufficient for `href` attributes because it does not stop javascript: URIs. The scheme must be validated, and it's important to provide a single shared helper function rather than duplicating this validation across components, which can easily lead to drift.
**Prevention:** Use `URL()` parsing to validate schemes and strictly allow only `http:` and `https:`, returning an empty string or safely dropping the link if the validation fails.
