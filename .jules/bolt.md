## 2024-05-18 - [SQLite Derived Tables vs Correlated Subqueries]
**Learning:** In SQLite, a query using `LEFT JOIN` on a derived table (e.g. `(SELECT movie_id, AVG(...) GROUP BY movie_id)`) executes the aggregation for the *entire* table before joining and applying limits, causing significant performance overhead on paginated results. For small limits, correlated subqueries in the SELECT clause (e.g. `(SELECT AVG(...) FROM user_ratings WHERE movie_id = m.id)`) are much faster (e.g. ~0.001s vs ~0.19s for 50 records) provided an index exists on the foreign key (e.g. `user_ratings(movie_id)`).
**Action:** When writing paginated queries with aggregations in SQLite, prefer correlated subqueries over derived tables. Ensure the necessary indexes exist.

## 2025-02-12 - [SQLite Composite Covering Index for Correlated Subqueries]
**Learning:** When using correlated subqueries in SQLite for aggregations (e.g., `SELECT AVG(rating) FROM user_ratings WHERE movie_id = m.id`), a single foreign key index (e.g., `user_ratings(movie_id)`) can still result in slower execution because the database must fetch the actual rows to evaluate the aggregate. A composite covering index (e.g., `user_ratings(movie_id, rating)`) allows SQLite to satisfy the entire subquery purely from the index data pages without retrieving the underlying table rows, drastically reducing execution time (e.g. from ~10.6s to ~0.7s for 200k ratings).
**Action:** When optimizing correlated subqueries for single-table aggregations in SQLite, use a composite covering index that includes both the `WHERE` clause column(s) and the aggregated column(s) (e.g., `idx_table_fk_val ON table(fk, val)`).
