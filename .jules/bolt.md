## 2024-05-18 - [SQLite Derived Tables vs Correlated Subqueries]
**Learning:** In SQLite, a query using `LEFT JOIN` on a derived table (e.g. `(SELECT movie_id, AVG(...) GROUP BY movie_id)`) executes the aggregation for the *entire* table before joining and applying limits, causing significant performance overhead on paginated results. For small limits, correlated subqueries in the SELECT clause (e.g. `(SELECT AVG(...) FROM user_ratings WHERE movie_id = m.id)`) are much faster (e.g. ~0.001s vs ~0.19s for 50 records) provided an index exists on the foreign key (e.g. `user_ratings(movie_id)`).
**Action:** When writing paginated queries with aggregations in SQLite, prefer correlated subqueries over derived tables. Ensure the necessary indexes exist.

## 2024-05-18 - [Python Substring Matching List Comprehension vs Generator Expression]
**Learning:** While testing list comprehensions vs generator expressions for `any()` substring checks, list comprehensions (`any([marker in text for marker in markers])`) appeared faster in micro-benchmarks for small string sets due to lower iteration overhead. However, this is a dangerous anti-pattern as it completely defeats the core feature of `any()`: short-circuiting. It forces Python to evaluate the entire loop and build a boolean list in memory before passing it to `any()`. For long texts or when matches occur early, this severely degrades performance and wastes memory. Moving tuples to module-level constants, however, correctly avoids re-allocation overhead on every function call.
**Action:** Never replace generator expressions inside `any()` with list comprehensions just to win a micro-benchmark on small sets; preserve short-circuiting behavior. Do, however, move locally defined constant tuples to module-level constants to avoid repeated allocation overhead.
